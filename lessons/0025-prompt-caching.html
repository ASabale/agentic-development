Lesson 0025 · Phase 3 depth · ~12 minutes

Prompt caching

Append-only prefixes are a cost feature. Rewrite the system prompt and you pay twice.

Your one win today Explain a cache hit as “the same rendered prefix, so the provider reuses KV state,” and name the harness rule that protects it: stable head, append-only tail.

1 · What is being cached

When a model reads a prefix it builds intermediate key–value (KV) tensors so later tokens can attend back. Prompt caching stores those tensors for a reusable prefix. The next request that starts with the same rendered bytes can skip that work: cheaper input (OpenAI: discounts up to ~90% on cached reads) and faster time-to-first-token.[1]

It caches KV state, not your secrets as a document store. A later request still has to match the prefix. Change the system prompt, reorder tools, or insert a message at the head, and everything after the first difference cannot hit.

Harness rule Put static content first (system, tool schemas, long instructions). Append new turns and observations at the end. Never rewrite history “to be tidy.” Tidiness is a cache miss — and a correctness bug besides (0004).

Willison already flagged this as why coding agents are append-only.[2] OpenAI’s cookbook says the same: tools and their order must be identical to stay in the prefix; add new messages at the end.[3]

2 · Numbers that change, mechanics that don’t

  • Minimum prefix length before anything caches (OpenAI documents 1,024 tokens on recent families; check the page for the model you use).[1]
  • Reads are cheap; on newer families writes can cost a premium (OpenAI: 1.25× uncached on GPT-5.6+). Worth it when you reuse.
  • Compaction (0004) replaces the prefix — it is a deliberate cache break. Do it when rot demands, then keep the new recap stable.

Measure cached_tokens / cache-read hits. If your agent is 4× chat (0023) and your hit rate is 0%, you are burning the triangular prefix at full price.

Interview angle “How do you keep agent cost down?” After the envelope: append-only for cache; don’t shuffle tools; don’t put the user id at the start of the system prompt if it varies per customer (that turns the whole prefix cold). Compaction is a cost/quality trade, not free.

3 · Retrieval practice

1. A cache hit requires…

Correct. Prefix bytes (and cache-affecting settings). Output can differ; that is the point of a new call.
Not user-id magic, not matching answers. Same prefix. Option 2.

2. Inserting a new system sentence at the top of every turn…

Correct. Dates and per-turn extras belong at the tail (or in a dedicated later message), not in the static head.
More information at the head is a miss, not a hit. Option 3.

3. Why must tool schema order stay stable?

Correct. Cookbook: tools and their order are part of the prefix. Call order at runtime is a different question.
The model can call in any order. Schema alphabetization is a myth. Option 1.

4. Compaction vs caching?

Correct. Break, then append-only on the new recap. Both are valid; they trade at different times.
Not the implementation of cache, and not a ban. Rewrite once, then hold still. Option 3.
