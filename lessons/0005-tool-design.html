Lesson 0005 · Phase 2: Core patterns · ~12 minutes

Tool design as API contract

The schema is not docs for humans. It is part of the prompt.

Your one win today Treat a tool definition the way you would treat a public API: name, description, and JSON schema are the agent's only view of the world. Design them as an agent–computer interface, not as afterthought comments.

1 · A tool is a contract the model can see

A tool definition has three fields that matter:[1]

  • Name — a verb the model can say. get_weather, not weatherHelperV2.
  • Description — when to use it, when not to, what it returns. This text is injected into context. It is prompt engineering.
  • Parameters — a JSON Schema for arguments. Types, required fields, enums, descriptions per field. OpenAI’s strict: true (Structured Outputs) can constrain decoding so arguments match the schema, not merely look like JSON.[1]

Anthropic’s name for this surface is the agent–computer interface (ACI): invest in it the way product teams invest in HCI. Poka-yoke the arguments (require absolute paths; reject ambiguous ids), write descriptions as if onboarding a junior engineer, prefer a few high-level tools over a swarm of overlapping ones.[2]

ACI The contract between a non-deterministic model and deterministic code. The model never sees your implementation — only the schema and the observation. If the contract is sloppy, the model will call sloppily.

2 · Errors are observations

When a tool fails, do not swallow it. Return a compact, truthful observation: what failed, what the model can change next time. 12-factor Factor 9: compact the error into the window so the model can self-heal; cap retries so it cannot spin.[3]

If the model emitted two calls and you skip the second, still return a result for it (an error with a one-line reason). A missing observation desynchronizes the transcript — lesson 0002.

3 · Fewer, better tools

More tools are not more capability. Overlapping names confuse selection. Anthropic’s SWE-bench work spent more effort on tool descriptions than on the system prompt; small wording changes dropped error rates sharply.[2] The practical rules:

  • One tool, one job. If two tools could both apply, the description must make the split obvious.
  • Return token-efficient results. A 40-row table beats a 400-line JSON dump. The observation consumes the window.
  • Namespace if you must (jira.create_issue vs github.create_issue).
  • Do not expose a raw SQL tool to a customer-facing agent. Expose lookup_order(id). The ACI is also a security boundary — lesson 0012.

Anthropic’s later tool post adds the loop you use to get those descriptions right: build and grade the tools with an agent, on real tasks, and read the failures.[3] A schema that looks precise in a doc and still gets the wrong argument is a tool bug. Fix the description or the shape. Do not add a seventh overlapping tool.

Interview angle “How would you design tools for a support agent?” Talk ACI, not frameworks. Name, description, schema; poka-yoke ids; compact errors; few tools; observations as the only channel. Mention that tool descriptions are in the prompt, so they compete with everything else for attention. Say you would eval the tools, not only the agent.

4 · Retrieval practice

1. Why is a tool description “prompt engineering,” not documentation?

Correct. The model never reads your wiki. It reads the description sitting in the window, every turn.
Descriptions live in the prompt. They are not training data and not for human reviewers. Option 3.

2. A lookup tool returns a 12,000-token JSON blob. What is the real cost?

Correct. Observations are context. Bloated results cause rot (lesson 0004). Compact what you return.
Models can read JSON. The cost is the window, not a crash. Option 1.

3. Best response when a tool throws?

Correct. Errors are observations. Self-heal once or twice; then stop or escalate. Factor 9.
Hiding failure removes the only signal the model has. Restarting throws away working memory. Option 2.

4. “Give the agent the Stripe SDK as one big tool” is a bad ACI because…

Correct. Expose the three verbs you mean (create_payment_link, …). The ACI is also a security boundary.
Schema and JSON are fine. The problem is a wide, unsafe, overlapping surface. Option 3.
