Lesson 0010 · Phase 2: Core patterns · ~12 minutes

RAG for agents

Retrieval is a tool inside the loop, not a preprocessor you run once.

Your one win today Define RAG in one sentence, name the chunking failure Anthropic actually measured, and say when an agent should search instead of having docs glued to the prompt.

1 · RAG, without the product

RAG Retrieval-augmented generation: fetch relevant pieces of a knowledge base and append them to the prompt so the model can ground its next tokens in those pieces, rather than in parametric memory alone. [1]

Classic pipeline, still worth knowing cold:

  1. Chunk the corpus (pages, paragraphs, overlapping windows).
  2. Index the chunks — embeddings, keyword (BM25), or both.
  3. At query time, retrieve top-k, optionally rerank.
  4. Stuff them into the window and generate.

That pipeline is a workflow (lesson 0003): your code always retrieves, then always generates. It is the right default when the question is “answer from this corpus, once.”

2 · The failure RAG actually has

Anthropic’s Contextual Retrieval post names the boring, load-bearing bug: chunking destroys context. A chunk that says “the revenue grew 3%” is useless if you have lost which company and which year.[1]

Their fix is not a new database. It is Contextual Embeddings + Contextual BM25: prepend a short, chunk-specific context (model-written) before you embed and before you index for keyword search. They report a 49% drop in retrieval failures, 67% with a reranker.[1]

Interview-useful morals:

  • Retrieval quality is often the bottleneck, not the generator.
  • Keyword search is first-class. Hybrid (BM25 + embeddings) is the grown-up default.
  • “We use RAG” is not an architecture. Say how you chunk, index, and measure miss rate.

3 · Agentic retrieval: search as a tool

Agents change the topology. Instead of stuffing the likely docs up front, you give the model a search tool (and a read tool) and let it pull just-in-time. Factor 3 called this progressive disclosure: keep pointers, load bytes when needed.[2]

Pre-retrieve (workflow)Search-as-tool (agent)
WhenQuery known; corpus small enough to guess wellWhat to read depends on what you find
CostOne retrieval + one generationSeveral tool calls; more tokens, more latency
FailureWrong chunks, silentlyBad queries, recoverable if the tool returns misses honestly

You can combine them: a cheap first retrieve for likely context, plus a search tool for the residue. That is still a workflow with an agentic pocket — which is how production systems actually look.[3]

Interview angle “Should we RAG or agent-search our wiki?” Strong: start with hybrid retrieval and measure miss rate (contextualize chunks). Promote search-as-a-tool when the next document depends on the last one. Never say “RAG” without saying chunking, hybrid index, and an eval set of questions with known passages.

4 · Retrieval practice

1. RAG, stripped of vendors, is…

Correct. Retrieve, then generate. The window still exists; you just put evidence in it.
Not training, not replacing the window. Stuff evidence into the prompt. Option 2.

2. Anthropic’s contextual retrieval targets which failure?

Correct. Prepend chunk-specific context before embedding and before BM25. Measured drop in failed retrievals.
The bug is lost context from chunking, not a GPU or theory limit. Option 3.

3. Prefer search-as-a-tool over pre-retrieve when…

Correct. That is the agent test again: the path depends on discovery. If the corpus is tiny, just put it in the prompt.
Purchases and tiny corpora do not justify a loop. Discovery does. Option 1.

4. A grown-up RAG answer in an interview names…

Correct. Retrieval is often the bottleneck. If you cannot say how you measure misses, you do not have RAG; you have hope.
Vendor and generator are the least interesting parts. Option 3.
