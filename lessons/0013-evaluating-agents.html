Lesson 0013 · Phase 3: Production · ~12 minutes

Evaluating agents

A task, a trajectory, a grader. Without this you are guessing in production.

Your one win today Define an agent eval the way Anthropic does, name three kinds of grader, and refuse to grade a rigid path when you meant to grade an outcome.

1 · What an eval is

Anthropic, Demystifying evals for AI agents:[1]

Eval Give an AI an input (a task, often with an environment), run it, apply grading logic to its output — and, for agents, to the trajectory and the world it left behind. The post focuses on automated evals you can run in development, without live users.

A grader scores some aspect of the run. One task can have several graders, each with several assertions. Three types, used in combination:

GraderExampleStrengthFailure
Code-basedUnit tests, file exists, SQL row written, regex on outputCheap, deterministic, replayableBlind to quality that tests don’t encode
Model-based (LLM-as-judge)“Does this reply refuse the jailbreak?”Covers fuzzy propertiesThe judge can be wrong; audit it
HumanExpert review of tracesGold for new domainsSlow; use to calibrate the other two

Two jobs evals do, do not mix them:

  • Capability: did this change make the agent better at the hard things?
  • Regression: did this change break what already worked?

Anthropic’s warning: early on, dogfooding feels faster than evals. After you ship, building without them becomes a reactive loop — wait for complaints, reproduce by hand, fix, hope nothing else died. Claude Code itself started on employee feedback and only later grew evals (concision, file edits, then over-engineering).[1]

2 · Grade outcomes, audit graders

Agents take many paths to the same goal. Over-specifying the path (“must call tool A then B”) punishes a better plan. Prefer assertions on the world: the file is correct, the refund is the right amount, the citation is in the retrieved set. Use path assertions sparingly, for safety (“must not call drop_table”).

Graders are software. They have bugs. Anthropic’s cautionary tale: a grader’s decimal-place strictness demolished scores until someone read the transcripts and fixed the grader, not the agent. Always sample traces. A 40-point swing may be the ruler, not the student.[1]

Chip Huyen’s broader AI-engineering stance is the same instinct: evaluation-first. If you cannot say what “better” means, you cannot iterate.[2]

Interview angle “How would you eval this support agent?” Strong: a held-out set of tickets with expected world-state (refund issued iff policy matches); code graders for policy; an LLM-judge for tone, audited against a human sample; a regression suite that must stay green; traces on every fail. Weak: “we’d look at thumbs-up in prod.”

3 · Retrieval practice

1. An agent eval, in Anthropic’s wording, is…

Correct. Task + run + grader. Production monitoring is complementary, not a substitute.
Live traffic and vendor leaderboards are not a development eval. Option 2.

2. You should usually grade an agent on…

Correct. Many paths, one world-state. Reserve path checks for “must not.”
Rigid paths and thought-policing punish good agents. Grade the world. Option 3.

3. A capability eval and a regression eval differ because…

Correct. Same machinery, two questions. You need both once you have a baseline.
The split is the question you ask, not the grader species or the calendar. Option 1.

4. Scores crater after a grader change. First move?

Correct. Anthropic’s decimal-place story. Audit the grader before rewriting the agent.
Do not treat the grader as scripture, and do not drown it in tools. Read traces. Option 3.
