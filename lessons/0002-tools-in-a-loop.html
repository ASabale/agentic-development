Lesson 0002 · Phase 1: Foundations · ~12 minutes

Tools in a loop

The anatomy of one step: call → execute → observe.

Your one win today Draw the five-step tool-calling flow from memory, and name which side — model or harness — does each step. This is the entire runtime of every agent you will ever ship.

1 · The model never touches the world

An LLM produces tokens. It cannot search, refund, or read a file. When it “uses a tool,” it is emitting a request — a structured blob that says “please run this function with these arguments.” Your code, the harness, is what actually runs.[1]

Harness The software around the model. It sends prompts, parses tool calls, executes functions, appends results, and decides whether to loop again. The model is a stateless function. The harness is the program.

OpenAI is blunt about the split of labor: “The API will not actually execute any function calls. It is up to developers to execute function calls using model outputs.”[2] Anthropic says the same from the other side: Claude never sees your implementation — only the schema you provided and the result you returned.[3]

2 · One step, five beats

OpenAI documents the canonical flow as five beats. Memorize this sequence; every framework is a costume on top of it.[1]

  1. You call the model with tools. The request includes the conversation so far, plus a list of tool definitions (name, description, JSON schema for arguments).
  2. The model returns a tool call — not an answer. Name of the function, arguments as JSON, and an id so you can match the result later.
  3. Your harness executes the function with those arguments. This is ordinary code: a weather API, a SQL query, a file read.
  4. You call the model again, appending the original call and the tool’s output, tagged with the same id.
  5. The model either answers or calls again. If it answers, the loop stops. If it emits another tool call, you go back to step 3.

Willison’s teaching version of the same loop is even plainer: the system prompt tells the model how to emit a tool tag, the harness regexes (or, in production, parses JSON) that tag out, runs the function, and stitches the result into the next prompt.[3] Modern APIs hide the tags behind tool_calls / tool_use fields. The mechanics did not change.

3 · Pairing results by id

The model may request several tools in one turn. Each call has an id (call_id on OpenAI, tool_use_id on Anthropic). You must return one result per call, even if you skipped or failed it.[1] Dropping a result is how loops desynchronize — the model thinks a tool is still in flight.

Observation The tool’s output, fed back into context. It can be JSON, plain text, or a compact error. Errors are observations too — not exceptions you hide from the model. That idea becomes Factor 9 later.

3b · Walk it, one beat at a time

The five beats are cheap to nod at and expensive to feel. Step through a scripted weather clerk. Nothing here calls an API — the model is fake; the split of labor is real.

4 · Why this is the whole runtime

Simon Willison’s consensus definition from lesson 0001 — an LLM agent runs tools in a loop to achieve a goal — is this five-beat cycle with a stopping condition.[4] Memory, planning, multi-agent, frameworks: all of them either (a) change what goes into the context before step 1, or (b) change what the harness does at step 3. None of them replace the loop.

Interview angle “Walk me through what happens when an agent calls a tool.” The strong answer names the five beats, says the API does not execute your function, and mentions pairing by id. Bonus: “the model is stateless; the harness holds the transcript.”

5 · Retrieval practice

Cover section 2. Four questions; instant feedback. Equal-length options, no formatting tells.

1. Who actually runs the function when a model “calls a tool”?

Correct. The API returns a request. Your code executes. OpenAI: “The API will not actually execute any function calls.”
The model emits a request, not an RPC. Execution is always your harness (for client tools). Option 3.

2. After executing a tool, what must you send back to the model?

Correct. Pair by call_id / tool_use_id. The transcript of call + result is the model's short-term memory of that step.
The result has to be bound to the call that produced it. Dropping history, or sending a new goal without the observation, breaks the loop. Option 1.

3. A model emits two tool calls in one turn. You run only the first. What should you do?

Correct. Every tool call needs a matching observation, including skipped or failed ones. Otherwise the model's view of the world is missing a beat.
Desynchronizing the transcript is how agents go off the rails. One result per call, always. Option 2.

4. Which statement is the clean split of labor?

Correct. Decide vs. do. That split is the whole architecture. Keep it when we add memory, HITL, and multi-agent.
Models are stateless and cannot execute your functions. Decision is the model's; execution and looping are yours. Option 3.
