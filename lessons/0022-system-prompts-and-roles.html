Lesson 0022 · Phase 1 depth · ~10 minutes

System prompts and roles

The prefix the user never sees. Factor 2: if you cannot grep it, you do not own the agent.

Your one win today Name the three common roles, say what the system prompt is for in a coding/agent harness, and refuse to let a framework hide that string.

1 · Roles are just labeled slices of the prefix

A chat-templated prompt is a completion string with names attached. The usual cast:[1]

RoleWho writes itTypical job
system / developerYou, once per product (plus tool schemas)How to behave; what tools exist; output shape; safety rails that are text, not a real lock
userThe human, or a webhook, or another agentThe goal for this turn
assistantThe model (or you, in few-shot exemplars)Thoughts, answers, tool-call blocks
tool / function outputThe harnessObservations, paired by id (lesson 0002)

Different vendors spell this differently. OpenAI has used system then a stronger developer role on some models. Anthropic puts a lot of “system” in a top-level system parameter rather than a message. The idea does not change: there is a prefix the end user does not author, and it is the highest-leverage document in the product.

System prompt The instructions, not shown in the UI, that start every conversation. Coding agents’ system prompts run to hundreds of lines — Codex’s published template is a useful specimen of what actually makes a loop behave. [1]

2 · Own the string

12-factor Factor 2: own your prompts.[2] If LangChain or an “agent SDK” concatenates a hidden preamble you cannot print, you cannot:

  • eval a change (“did this sentence fix over-engineering?”)
  • debug a weird tool call (the instruction may already forbid it — or invite it)
  • know what leaked when a user jailbreaks “ignore previous instructions”

Treat the system prompt as source code. Version it. Diff it. Put a hash of it on traces (lesson 0026). Do not let it rot as a 2,000-line novel; Factor 10 applies to prompts too.

Tool schemas sit next to it in the prefix. They are also prompt. Changing a description is a prompt change (lesson 0005).

Interview angle “What’s in your system prompt?” Strong: I can cat it; it names tools, output rules, and stop conditions; tool descriptions are separate files we review like APIs; we eval prompt diffs. Weak: “whatever the framework default is.”

3 · Retrieval practice

1. The system prompt is powerful because…

Correct. High leverage because it is always there. Not a lock: injection exists (lesson 0027). Not compiled into weights.
Not a fine-tune, and not an override-proof vault. Tokens in the prefix. Option 3.

2. Factor 2 in one line?

Correct. Hidden framework preambles are undebuggable source code.
Engineers write prompts; they are not deprecated. Own the string. Option 1.

3. Tool descriptions belong…

Correct. ACI is prompt surface. A description change is a prompt diff.
Wikis the model never reads do not count, and samplers are not docs. Option 2.

4. A 4,000-line system prompt is a smell because…

Correct. Factor 10 for prompts. Cache actually *loves* a stable system prefix (0025) — length is still attention cost.
No two-sentence cap, and system text *is* cacheable. The smell is rot and eval. Option 3.
