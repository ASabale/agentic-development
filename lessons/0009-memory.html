Lesson 0009 · Phase 2: Core patterns · ~12 minutes

Memory

If it is not in the window, the model does not know it. Everything else is a tool.

Your one win today Draw two boxes — in-context and external — and refuse to call a vector database “memory.” Memory is notes the agent can write and read. Vectors are one retrieval mechanism among several.

1 · Two kinds, one rule

Weng’s split is still the right one:[1]

Short-term / in-context

The current window: system prompt, this conversation, this trial’s tool calls. Lesson 0004. Finite, expensive, rotting.

Long-term / external

Anything that survives a new call: files, a database, a ticket, a git log. The model sees it only when some tool puts a slice into the window.

Willison, on the consensus definition of an agent: the tool-call conversation already is short-term memory. “If you want long-term memory the most promising way to implement it is with an extra set of tools.”[2]

Memory (operational) Structured note-taking. The agent writes to persistent storage so it can track progress across tasks and sessions without keeping everything in active context. Reading those notes is a tool call.

Anthropic’s memory tool is literally a filesystem under a directory, executed client-side: create, read, update, delete files that persist between sessions.[3] Claude Code’s “memory” is markdown files the harness re-injects. There is no magic neuron.

2 · Vectors are retrieval, not memory

A vector store answers “find chunks like this query.” That is RAG — next lesson. It is a fine backend for one memory tool (search_notes(query)). It is a terrible synonym for memory, because:

  • Most of what an agent needs to remember is exact: the ticket id, the branch name, the failing test. Grep beats cosine similarity.
  • Embeddings forget structure. A decision log is a sequence, not a bag of nearest neighbors.
  • You still have to decide what to write, when to retrieve, and how much to paste into the window. That is context engineering. The database does not do it for you.

Write less than you think. Every byte you store will fight for attention when it returns. Prefer pointers (path, id, URL) and fetch just-in-time — Factor 3 again.[4]

Interview angle “How would you add memory to this agent?” Weak: “Pinecone.” Strong: the conversation is STM; for LTM I’d give it a notes tool and decide, deterministically, what gets written (progress, decisions, user prefs) and what gets retrieved (pointers first). I’d eval whether retrieval helps before I buy a vector database.

4 · Retrieval practice

1. Long-term memory, operationally, is…

Correct. Willison: long-term memory is an extra set of tools. Anthropic: a filesystem of notes.
Models are stateless (lesson 0004). Vectors are one backend. Notes-plus-tools is the thing. Option 2.

2. Why is “we added memory (Pinecone)” a sloppy sentence?

Correct. You can remember with files and grep. You can retrieve without remembering. Name the verb.
The sloppiness is confusing a retrieval backend with the memory policy. Option 3.

3. Best default for a ticket id the agent must not scramble?

Correct. Exact facts want exact storage. Cosine similarity is how ids get mangled.
Nearest-neighbor and pretraining are how you lose the id. Option 1.

4. The live tool-call transcript is which kind of memory?

Correct. Willison: tools-in-a-loop already has STM baked in. Logs on disk are LTM only if a tool reads them back.
A log file the model never sees is not memory. The replayed window is STM. Option 3.

  • Two boxes: in-context / external. One rule: unseen = unknown.
  • New glossary terms: short-term memory, long-term memory, memory tool.
