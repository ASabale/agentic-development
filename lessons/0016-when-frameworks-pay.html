Lesson 0016 · Phase 4: Advanced · ~12 minutes

When frameworks pay

The loop is fifty lines. You buy a runtime for the parts that are not.

Your one win today Draw the buy-vs-build line: own the loop until you need durable execution, interrupts between select and invoke, or graph-shaped control flow worth checkpointing. Name LangGraph as a runtime, not as “an agent.”

1 · The loop is not the product

Willison: a simple tool loop is a few dozen lines on top of an LLM API. A good loop is much more work — and the extras are engineering, not intelligence.[1]

Anthropic, same direction: the most successful production systems were not complex frameworks. Start with the API; many patterns are a few lines. Frameworks ease boilerplate and then hide prompts and responses, which makes debugging worse.[2]

Horthy: he does not see a lot of frameworks in production customer-facing agents. Founders rolling the stack. “Agents” that are mostly software.[3]

So the default in this course remains: write the five beats. Own the prompt. Own the window. That is lessons 0002, 0005, 0011, 0014.

2 · What LangGraph actually sells

LangGraph’s own positioning is unusually honest. It is “a low-level orchestration framework and runtime for building, managing, and deploying long-running, stateful agents.” The durable value is not a hidden ReAct prompt. It is durable execution, streaming, human-in-the-loop, persistence.[4]

The vocabulary, which you should be able to draw:

  • State — the snapshot. Schema + reducers (how updates merge). This is Factor 12 with types.
  • Nodes — functions. May call an LLM, or just run code. “Nodes do the work.”
  • Edges — functions that pick the next node, including conditional ones. “Edges tell what to do next.”
  • Compile — validate the graph; attach checkpointers and breakpoints. You must compile before you run.

Under the hood: message-passing in Pregel-style super-steps. Nodes that can run together do; the graph halts when nothing is in flight. That is a workflow engine that is allowed to loop — which is why it can express both lesson 0003’s patterns and lesson 0002’s agent loop as the same object.

When it pays You need to pause between select and invoke, resume after a crash, branch on state, fan-out and join, or stream tokens to a UI — and you would rather not build a checkpointer. You still write the prompts. You still own the schemas.

Stay with a loop

Linear tools-in-a-loop. Few intents. You can persist a JSON thread yourself. You want every prompt in grep.

Buy a runtime

HITL as a first-class interrupt. Multiple writers on state. Long-running jobs. You want a graph picture your team can argue about.

Interview angle “Why didn’t you use LangGraph?” Strong: the loop is trivial; we needed X; until we needed durable interrupts / graph joins we kept fifty lines we can debug. If we did use it: we bought checkpointers and interrupts, not a personality. Weak: “LangChain is industry standard so we started there.”

3 · Retrieval practice

1. Anthropic’s advice on frameworks, compressed?

Correct. Extra layers obscure prompts and responses. Many patterns are a few lines of API code.
Tool count does not force a framework, and APIs are not legacy. Option 2.

2. LangGraph’s three nouns?

Correct. Nodes do the work; edges pick next; state is the snapshot with reducers.
Not personalities, and prompts are still yours. State / nodes / edges. Option 3.

3. A good reason to adopt a graph runtime?

Correct. Interrupts and checkpointers are the product. Prompts and schemas stay yours.
If it writes your prompt or your schema, you no longer own Factor 2 and 4. Option 1.

4. “LangGraph is an agent” is wrong because…

Correct. Low-level orchestration. You can build a workflow or an agent on the same graph.
It can loop, and it can call tools. It is not itself the agent. Option 3.
